> Note (2026-10-25): history. Laundry, lodging and restaurants (session 32), then salons, pharmacies, the GROCERY and HYBRID types, recipes and tips (migration 0112) were removed since; A1–A4 and A6 are moot with them. A5 (refunds of split-paid sales with store credit) still stands.

A second full audit of the code (session 31), after sessions 20–30 added customers, counter controls, integrations and seven business types (ADR-0017 … ADR-0025). It checks the same two things as [the first audit](AUDIT-2026-10-19.md):
1. Does what is built work end to end, and does it keep the house rules in `CLAUDE.md`?
2. What does the spec, `INDUSTRIES.md` or an ADR promise that is missing?

Defects that needed no decision were fixed in this session. What needs a decision is in §4; work left open is in `LEFTOVER.md` under "Audit 2026-10-21". This document is a snapshot.

## 1. How the audit was done
- **Eight read-only reviews**, each reading the code (schema, migration SQL, services, routes, screens), not the docs:
  1. platform, tenancy, security, integrations (§4, §6.1, §6.11, §8, §14);
  2. catalog, retail checkout, cash, tax (§6.2, §6.3, §6.7, §9, §12, §13);
  3. restaurant and counter service (§6.4);
  4. inventory, purchasing, books (§6.5, §6.6, §6.8, §10);
  5. salons and lodging (ADR-0022, ADR-0023);
  6. laundry and pharmacies (ADR-0024, ADR-0025);
  7. offline sales, terminal API, reports, operations, tests (§5.2, §6.9, §6.10, §11, §15–§18);
  8. wiring: 467 routes against `openapi.json` (identical both ways), 221 admin client calls against the BFF allow-list, 312 admin server calls, 153 POS calls, 517 E2E calls, body fields against the zod schemas, guide quotes, EN/FIL keys, TODO markers.
- Each finding was checked against the code before it was fixed. Findings already tracked in `LEFTOVER.md` or the first audit were not repeated.
- **Fixes** were made by five fixers on disjoint files, then reviewed together. Every fix has a new integration test (listed in §2).

### What held up
- RLS, `FORCE`, grants, export grants and append-only triggers on every table from migrations 0074–0106. Every `SECURITY DEFINER` function has `search_path`. There is no raw SQL interpolation of input.
- One ledger entry per document through `post()`, in the same transaction, for every new document type: store credit, packages, tips, pack openings, folios, deposits, down payments, expiry write-offs and supplier notes. Backfills wrap every table they read in `NO FORCE`/`FORCE`.
- Promotion parity between the server and the offline engine. The checkout entry points: idempotency, one transaction, header buckets.
- No client call is refused by the BFF, and no call targets a missing route. All alert `runbook_url` anchors exist. `BUSINESS_GAUGES` equals `platform_metrics()`. EN and FIL keys are in parity (admin 3199, POS 1105). There are no `.only`, `.skip` or `.todo` in the tests.

## 3. Left open after the first round: work
_All of these were done later in the session (§6). What is still open is in `LEFTOVER.md` under "Audit 2026-10-21"._
- **Category management has no screen**: no tree, and no category on the product form. So the plan-gated "By category" report shows everything as uncategorised for a business set up through the admin. The same goes for UoM and tax-category creation, menu rename (`PATCH /v1/menus/:id`) and editing a laundry trip (`PATCH /v1/laundry/trips/:id`).
- Once a category screen exists, drop `uoms`, `tax-categories` and `categories` from the BFF allow-list and move the E2E scripts to the API.
- **Monitoring for the newer background jobs**: night-audit failures are only a log line, and nothing watches laundry notices. These need metrics, gauges, alerts and runbook sections.
- **The traceability audit does not compare the new balance-sheet accounts with their sub-ledgers**: store credit 2300, packages 2310, guest ledger 1150, guest deposits 2320, down payments 2330, tips 2210. It also has no lot invariants. Today those checks live only in test scenarios.
- **Restaurant:**
  - voiding a check does not release its share of the bill (medium);
  - checks cannot carry a customer, so store credit can't pay a check (small–medium);
  - a voided counter sale prints no "VOID" slip for a printed kitchen (medium).
- **Lodging:**
  - no overstay handling or "occupied" housekeeping state;
  - the manual night audit runs the branch in one transaction;
  - catch-up nights use the current rate.
- **Lodging deposits and folio payments may be taken at any drawer of the legal entity** (ADR-0023 §5.2). Their journal lines carry the stay's branch, while folio payments carry the drawer's, so branch cash in the books can differ from the drawers.
- **Salon:**
  - archiving a staff member or adding time off ignores their future appointments;
  - checkout does not check that the staff member does the service;
  - a fractional return of a session line errors instead of refusing.
- **Laundry:** a self-service cycle queued in the future cannot be stopped; returning a cycle sale leaves its machine run.
- **Store credit in the Z-reading and by-tender report:** a return split between store credit and cash is counted entirely under its refund method.
- **Offline:**
  - a price or promotion back-dated after a snapshot was cut can quarantine a valid offline sale as `TOTAL_MISMATCH`;
  - `catalog_versions` is not bumped by counter-menu availability (the root of the tracked "86'd item sells offline").
  - Some API-only routes and reads have no screen, by design: deposit apply/forfeit, and the reads for API keys.
- **Tests:**
  - a return with several package-session lines (now added);
  - an offline sale that opens packs or draws expired lots outside pharmacy;
  - an API-key scope for appointments (`appointments.read`);
  - a package line returned in part can leave a centavo on Sales returns.
- **i18n:**
  - English `aria-label`s at four places;
  - English browser-tab titles on all admin pages (systemic);
  - example placeholders.
- The stale `TODO(Phase 6)` in applied migration 0013 stays, because applied migrations are never edited.
