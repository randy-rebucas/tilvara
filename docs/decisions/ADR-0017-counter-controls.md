# ADR-0017: Counter controls — line discounts, approved price changes, held carts, exchanges

- Status: Accepted (2026-10-19, session 20). Built from the 2026-10-19 audit (§3.2). The user chose how a price change is approved: a manager who holds `sales.price_override` types their own email and password at the till (and their code if they use two-step sign-in), not a PIN.
- Builds on ADR-0008 (tax engine), ADR-0009 (checkout), ADR-0011 (returns).

## Decision
1. **Line discounts.** A cart line takes `discount` (an amount) or `discountRate` (a fraction in (0, 1], "0.1" = 10 %), never both. The rate is applied by `@1pos/tax` to the line's gross and rounded like any amount, so the server computes the discount; either form needs `sales.discount` at the branch (checked in `TaxService.computeCart`, the one pricing path). SC/PWD and an ordinary discount still never stack on one line. The till offers the control only to people holding `sales.discount` and only online (ADR-0015 §1 keeps discounts off offline sales).
2. **Price changes need an approval document.** `POST /v1/price-overrides` creates an append-only `price_overrides` row: branch, item, the list price in force and its id, the new unit price (same basis as the list), the reason, who asked, who approved and how (`SELF` or `CREDENTIALS`), valid 30 minutes.
   - Without credentials the person asking must hold `sales.price_override` at the branch (`SELF`).
   - With credentials the API checks them exactly like a sign-in (`AuthService.verifySecondPerson`): lockout, password, account active, the 6-digit code for an approver with two-step sign-in. Failures count towards the approver's lockout. The answers are 403, never 401, so the cashier is not signed out. The approver's own grants in this business must include `sales.price_override` at the branch. Nothing about the password is stored. The route is rate-limited per address and per approver account.
   - Each refusal and approval is in the business's audit log (`sale.price_override_refused` / `_approved`). The email typed is never logged.
3. **Using an approval.** A cart line carries `priceOverrideId`. `computeCart` checks the approval: it must be for this branch and item, asked by this cashier, not expired and not used. The line is then priced at the approved unit price (VAT and SC/PWD apply as usual). The sale line stores `unit_price` = the approved price, `price_id` = the list price it replaced and `price_override_id`. Two database guards back this up: a unique index (one approval prices one sale line) and an insert trigger (the approval matches the line's item, price and branch).
4. **Held carts are not financial records.** `held_carts` keeps a cart's lines as the counter sent them (item, quantity, discount, approval id, SC/PWD refs and details) for a register. Nothing is priced, numbered, reserved or posted. Resuming re-prices the cart through the normal quote. It can be resumed by any cashier selling on that register on their own open shift. A row lock makes it come back once, and the row then goes `OPEN → RESUMED | DISCARDED`. A trigger requires `lines` and `beneficiaries` to be cleared when that happens, so SC/PWD names do not outlive the cart (privacy pack). Carts may stay open across shifts; Close shift says how many are open, it does not refuse.
5. **An exchange is a return and a sale in one transaction** (`POST /v1/exchanges`, required Idempotency-Key, on the cashier's own open shift, `sales.refund` + `sales.create`). The return is recorded by `ReturnsService.record` (ADR-0011 rules unchanged, its own number, posting and slip). The new sale is recorded by `SalesService.record`, and the refund is tendered first as a cash tender marked with `exchange_return_id`. The customer pays any rest with ordinary tenders, or gets the difference back as change. Both documents move the drawer as they always do (REFUND out, SALE in), so the drawer, the books and every report net to the cash that really changed hands. No new account and no new tender method were needed. The drawer check runs once, after both (the net may not go below zero). A trigger keeps the credit equal to its return's refund, at the same branch and shift, and it can be used once.
6. **Refund preview.** `POST /v1/sales/:id/returns/preview` prices a return without recording it, so the till can show the credit before taking money. It uses the same planning code as the return itself.
7. **Returns across registers.** The till's "Find an earlier sale" lets the person pick any register of the branch. The API already allowed a refund from today's drawer at the same branch. Cross-branch returns remain a tax-adviser question (LEFTOVER).

## Consequences
- `sales.price_override` now grants something; the role editor's label is accurate.
- Reports of discounts and price changes can read `sale_lines.discount` and `price_override_id` → `price_overrides` (list vs sold price, who approved). They are built in the reports slice.
- Tests: `counter-controls.test.ts` (10, incl. a code-required approver, the DB guards, concurrent resumes, exchanges both ways and an empty drawer), `isolation.test.ts` (+3 routes, +7 smuggling cases, 2 tables), `@1pos/tax` (+5), `test:e2e:pos:controls` (25).

## Not covered
- Offline: discounts, price changes, holds and exchanges need the connection (refused or hidden offline, as ADR-0015 ★ defaults leave them).
- A threshold above which a price change or discount needs a second person even for a manager (T5 thresholds are the user's call).
- An exchange paid back to a card or QR (waits on PayMongo refunds, D6).
- Held carts are never discarded automatically; the retention schedule proposes 7 days.
