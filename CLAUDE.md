# Tilvara — guidance for Claude sessions

**Start every session by reading `docs/STATUS.md`** (current phase, what's verified, next task), then `docs/BACKLOG.md` (the plan) and `docs/LEFTOVER.md` (open items left by finished slices). The full product spec is `docs/SPEC.md` (copy of the user's master prompt) — it is the source of truth for requirements.

## Working rules (from the spec)
- Work phase by phase (Inspect → Plan → Implement → Validate → Review → Document → Report). Don't start a later phase while an earlier phase has open critical defects.
- A feature is done only when schema, domain rules, API, authorization, failure handling, and automated tests all work. Never report UI-only or mocked work as complete; name dev adapters `Dev*`/`Fake*`.
- Never claim tests passed unless they were run in this session; quote the command.
- Never claim BIR accreditation/compliance. Production invoice issuance stays disabled until the compliance gate in `docs/compliance/` is cleared.
- Money/quantities: `@1pos/money` only, decimal strings on the wire, never JS numbers.
- New tenant tables are policed automatically: `rls-catalog.test.ts` (schema rules) and `isolation.test.ts` (needs fixture rows in every tenant table; every new `:id` route needs a case in its attack matrix).
- Tenant data: only inside `withTenant(pool, tenantId, fn)` from `@1pos/database`; tenant id from the server-side session only. Every new tenant table needs: `tenant_id`, `UNIQUE(tenant_id,id)`, composite FKs, `ENABLE`+`FORCE` RLS policy, grants for `onepos_app`, and a case in the cross-tenant test suite.
- Tax: compute only via `@1pos/tax` (ADR-0008) fed by the quote path (`TaxService.quote`); VAT status/rounding live in versioned `tax_profiles`. Effective dating uses the DB clock with a 5 s skew allowance (`effectiveNowSql` / `effectiveNow()` in `apps/api/src/common/clock.ts`), never `new Date()` or bare `now()` for "in force" checks.
- Checkout: only via `SalesService.create` (ADR-0009) or, for restaurant checks, `SalesService.createFromBill` (ADR-0014 §8: shares of a bill frozen by `computeCart`); both record through the private `record()` path: required Idempotency-Key + clientTransactionId, everything in one transaction. Sale header buckets = Σ lines + Σ `sale_charges`; the service charge ex VAT posts to `SERVICE_CHARGE_PAYABLE`, never Sales.
- Floor push (ADR-0014 amendment): a table whose changes the floor or KDS must see gets an `app_notify_floor()` AFTER trigger (0063); `/v1/restaurant/stream` carries no data, clients re-read through their normal routes. The POS reads it with `readEvents`/`useFloorPush` and keeps a slow poll as fallback.
- Counter service, kitchen printing, tips (ADR-0014 amendment, session 25): a counter sale's choices are expanded only by `expandCounterLines` (API) / `expandCounterCart` (till), the same rule on both sides; its kitchen copy is a COUNTER order written by `recordCounterOrder` inside `record()` (never through the table-service routes). Firing goes through `fireItems` (`apps/api/src/restaurant/counter.ts`). Tips live in `sale_tips` and post to `TIPS_PAYABLE`, never in `amount_due` or `sale_tenders`. Kitchen tickets are printed by desktop tills through the claim/printed/release terminal routes; never print inside a DB transaction. An item voided after its ticket printed asks for a VOID slip (`requestVoidSlips`, claimed like a ticket). Voiding a check reopens its bill and order (`reopenForVoidedCheck`, triggers 0108): a voided check's allocations no longer count as paid.
- Offline sales (ADR-0015): terminals reach only `@TerminalAuth()` routes, authenticated by `SyncService.authenticate` (the tenant comes from the credential). Offline envelopes are recorded only by `SalesService.recordOffline` (re-priced as of the snapshot, ignoring price/promotion rows created after it, through `record()`, delivery row in the same tx); refusals become quarantined `terminal_transactions`, never lost. Each envelope of a batch is validated alone: one the server cannot read is quarantined `VALIDATION_FAILED`, never failing the batch. The till engine is `@1pos/pos-offline` (no React; SQLite via `SqlDriver`).
- Financial/inventory/audit tables are append-only (trigger `app_forbid_mutation`); corrections are new rows.
- Stock: insert `stock_movements` only (sorted by variant id); the costing trigger sets cost/value and balances (ADR-0012). Inbound types other than RETURN/TRANSFER_IN/COUNT must pass `unitCost`.
- Negative stock (ADR-0012 amendment): per-branch `inventory_settings`; only a counter sale (`SalesService.create`) is refused under BLOCK, by `assertStockAvailable` (locks balances through `app_lock_stock_balances`); checks, offline sales and consumption are flagged, never refused. The costing trigger sets `below_zero` and writes the `stock.low` / `stock.below_zero` outbox events itself. Count sheets freeze on hand and post `counted − frozen` (`expected_quantity` on the count line); counting needs `inventory.count` or `inventory.adjust`.
- Packs and expiry (ADR-0020): a pack and its piece are two items linked by `pack_conversions`; opening packs is a `pack_openings` document with `UNPACK_OUT`/`UNPACK_IN` movements (`recordOpening`/`openPacksForSale` in `apps/api/src/inventory/packs.service.ts`; a sale short of pieces opens packs inside `record()`). Expiry lots (`stock_lots`, `stock_lot_movements`) are written only by the trigger `app_track_stock_lots` from stock movements; services pass `expiresOn`/`lotCode` on inbound RECEIPT/ADJUSTMENT movements and `lotId` on a removal, never write lots. Business type GROCERY gates like RETAIL: use `servesTables(type)`, never compare with 'RETAIL'.
- Promotions (ADR-0021): computed only by `applyPromotions` in `@1pos/pricing`, called by `TaxService.computeCart(…, { promotions: true })` (counter quote/sale/exchange/offline; never restaurant bills) and by the offline engine from the snapshot, so both price alike; the result is the line's ordinary `discount` plus `sale_lines.promotion_id`. A line with SC/PWD, its own discount or an approved price is never promoted. Promotion terms are immutable (trigger): rename or end only; changing terms = end + new.
- Salons (ADR-0022): appointments, service staff and packages only for `servesAppointments(type)` (SALON, HYBRID), refused otherwise by `assertAppointments`; a SALON's services take recipes ("supplies used") through `assertRecipes` without the restaurant plan feature. No double-booking: `AppointmentsService.plan` checks first, the GiST exclusion `appointment_services_no_double_booking` is the backstop (23P01 → 409 via the conflict map, which now also maps 23P01/23514 constraint names). A sale line may name `staffId` (rate kept on `sale_lines.commission_rate`) and `packageId` (priced at zero by `computeCart`). Packages are owed until used: `planPackages`/`recordPackages` inside `record()` credit `PREPAID_SERVICES` with the package's ex-VAT value (never Sales) and move each session's value into Sales; returns go through `returnPackages`. `customer_package_entries` is append-only with a per-package lock and a balance trigger. Tips split per staff in `sale_tip_shares` (deferred sum check). Service notes (`customer_notes`) may hold health information: audit by id only, deleted on anonymise.
- Lodging (ADR-0023): rooms, stays, folios and housekeeping only for `servesLodging(type)` (LODGING, HYBRID); `servesTables(LODGING)` is true. No double-booking: GiST exclusion on stays and room blocks (23P01 → 409 `ROOM_DOUBLE_BOOKED`). Folio entries are append-only on `GUEST_LEDGER` (1150), never below zero, per-folio lock; deposits are `stay_deposits` on `GUEST_DEPOSITS` (2320). Outlets charge a room only with the `ROOM_CHARGE` tender inside `record()` (counter sales and checks; refused offline). Folio payments and deposits are taken at an open drawer and count in `expectedCash`, never in sales. Room nights are posted only by the night audit (`NightAuditScheduler`, `NIGHT_AUDIT_INTERVAL_MS`, 0 in tests; `POST /v1/lodging/night-audit`) or by `prepare-check-out`, one entry per (stay, night), taxed through `@1pos/tax`. Guest registry rows are personal data (audit by field name only).
- Laundry (ADR-0024): job orders, machines, trips and laundry settings only for `servesLaundry(type)` (LAUNDRY, HYBRID), refused otherwise by `assertLaundry`; packages open to LAUNDRY through `usesPackages` (`assertPackages`), recipes through `assertRecipes`. A job's lines are priced by `priceJob` (`apps/api/src/laundry/job.ts`, on `TaxService.computeCart`, min quantity, the branch's express/delivery items added by the server) and frozen on the job; the claim is the third checkout entry point, `SalesService.createFromJobOrder` → `record()`: the down payment is applied first as the `JOB_DEPOSIT` tender (never accepted from a client or offline) with an APPLIED `job_order_deposits` row, any excess refunded in cash, storage fee line, packages redeemed and recipes consumed there; a claim sale is never voided (`CLAIM_SALE_NOT_VOIDABLE`). Down payments (`job_order_deposits`, append-only, per-job lock, never above the frozen total) post to `CUSTOMER_DOWN_PAYMENTS` (2330), forfeits to `FORFEITED_DOWN_PAYMENTS` (4120) with VAT; cash ones count in `expectedCash` (cash movements JOB_DEPOSIT/JOB_DEPOSIT_REFUND), never in sales. Self-service cycles: a counter sale line's `machineId` writes a `machine_runs` row in `record()` (queued behind the machine's current run; GiST no-overlap, 409 `MACHINE_BUSY`); online only. Notices: READY queues a `job_order_notices` row + `job_order.notice` event; reminders/final by the worker's `platform_flag_laundry_notices()`; the worker settles each via `laundry_notice_settle()` (email + `SmsSender`, dev only until D7).
- Pharmacies (ADR-0025): prescription classes (RX, ANTIBIOTIC, DANGEROUS) only for `servesPharmacy(type)` (PHARMACY, HYBRID; `assertPharmacy`); OTC medicines anywhere. Dispensing is checked and written only by `planDispensing`/`recordDispensing` inside `record()` (`apps/api/src/pharmacy/dispensing.ts`): every prescription-class line names a prescription item (on record or recorded with the sale), matched by `generic_key` (generic, strength, form), quantities in pieces (`piecesPerUnit` down the pack chain); `prescription_fills` is append-only under a per-item lock and trigger (a dangerous drug in one full fill, never offline); the dispenser holds `pharmacy.dispense` (+ `pharmacy.dangerous_drugs` and a `pharmacist_licenses` row in force) or a once-used `dispense_approvals` row from `verifySecondPerson`; returns give pieces back with `returnFills`. Expired or held lots are never sold where `expiredStockRule` is BLOCK (default for PHARMACY): `assertNotExpired` after pack openings, the lot trigger draws sellable lots first and marks `stock_lot_movements.expired`; offline sales are flagged, never refused. A sale opens packs up the chain (box → strip → piece, 3 levels) in `openPacksForSale`. Prescriptions are health data: audit by id/field name only, `PERSONAL_KEYS` covers the fields; anonymising a customer only unlinks them. A lot hold covers the whole pack family (`app_lot_held`, `unsellableAt`); a pack and its piece are the same medicine (`PACK_DRUG_MISMATCH`), and `drugsOf`/`tillDrugs` give an item the strictest class down its pack chain. Expired stock defaults to BLOCK for PHARMACY and HYBRID.
- Recipes (ADR-0014 §4): an untracked item with a recipe in force consumes its ingredients at checkout as `CONSUMPTION` movements of the SALE (`planConsumption` in `apps/api/src/restaurant/consumption.ts`); never post consumption as a separate document, and recipe-made lines are never restocked.
- Books: every new operational document posts one entry via `post()` (`apps/api/src/accounting/ledger.ts`) with rules from `@1pos/accounting`, in the same transaction (ADR-0013); `ledger.test.ts` compares GL to evidence.
- Migrations that back-fill data run as the migrator under FORCE RLS: wrap the backfill in `ALTER TABLE … NO FORCE ROW LEVEL SECURITY` / `FORCE` (see 0014, 0023, 0029, 0049) for every table it reads as well as writes (e.g. `tenants` when it loops over businesses), or it silently touches no rows. Check the row counts on the dev DB after migrating. In plpgsql triggers shared by two tables, read table-specific `NEW` fields in separate IF branches.
- Account security (ADR-0016): credentials (sessions, MFA factors/recovery codes, reset tokens) have no runtime grants; reach them only via `auth_*` SECURITY DEFINER functions. Account events outside a tenant are NULL-tenant audit rows written by those functions (`auth_record_event`). MFA is enforced in `AuthGuard` for privileged members (`PRIVILEGED_PERMISSIONS`) on tenant routes only. In tests, read NULL-tenant rows / `users` / MFA tables under `SET LOCAL ROLE onepos_platform`.
- Rate limits: `@RateLimit(...rules)` with `by: 'ip' | 'account' | 'terminal'`; counters in Redis when `REDIS_URL` is set (falls back to the process if Redis is down). Integration tests count in memory: `setup-env.ts` moves `REDIS_URL` to `TEST_REDIS_URL`; Redis tests pass `REDIS_URL` + a unique `RATE_LIMIT_PREFIX`.
- Data export (ADR-0016 slice 6): the worker exports every tenant table. A new tenant table needs `GRANT SELECT ON <table> TO onepos_worker` in its migration (a column list if it has a secret column, which then goes in `EXPORT_SECRET_COLUMNS`), or an entry in `EXPORT_EXCLUDED_TABLES` with the reason; `rls-catalog.test.ts` fails otherwise. Files go through `FileStorage` (`DevFileStorage` until D1).
- Runbooks: `docs/operations/README.md` (index). Privacy pack for the DPO: `docs/compliance/privacy/`. A new table or column holding personal data needs its row in `processing-register.md` and `retention-schedule.md`. drizzle runs all pending migrations in one transaction and silently skips a file whose journal `when` is not newer than the last applied one: never hand-edit `_journal.json` or reorder files (`migrations.test.ts` guards it); procedure in `database-migrations.md`.
- Support access (ADR-0016 slice 6): a token with `sgr` is a Tilvara staff support session (read-only, re-checked every request, `auth.support` set, `membershipId` null). A route a suspended or lapsed business must still use takes `@AllowReadOnlyBusiness()` and `mutate(…, { allowReadOnlyBusiness: true })`; nothing else may, except `SalesService.recordOffline` (session 21): a sale on a snapshot stamped `business_writable` and rung within its window is recorded and audited, anything else gets `readOnlyReason()`.
- Plan features (session 21): `assertFeature` for `restaurant`, `api_access`, `advanced_reports` (the analysis reports, via `AnalysisReportsService.read`) and `multi_entity` (a second legal entity). Everyday and statutory reports stay on every plan. Shift close refuses `OPEN_BILLS` (live orders when it is the branch's last open shift, or a bill part-paid on it); `cash.reconcile` + `openBillsReason` overrides, audited. Staff: `pnpm --filter @1pos/database support staff-add|staff-disable|staff-list`.
- The outbox worker connects as `onepos_worker` (`WORKER_DATABASE_URL`); only it may call `outbox_*` / `platform_purge_expired_idempotency`. A new handler that reads more tables needs an explicit column grant in a migration (`rls-catalog.test.ts` lists what the worker may read).
- NestJS: every constructor dependency uses explicit `@Inject(Token)` — Vitest does not emit decorator metadata (SWC native binding fails on this machine, so it was removed).
- Drizzle wraps pg errors (`Failed query: …`); the Postgres error is on `err.cause`.
- User guide (session 18): admin `/help` (`apps/admin-web/src/lib/guide.ts`, copy `guide.*`) and the counter's guide (`apps/pos-desktop/src/lib/guide.ts`, ? or F1). A new admin area or counter screen gets its part or lines (and a `TOPIC_BY_PATH` entry for a new admin path); a changed button label means updating the guide line that quotes it (no test catches that). `guide.test.ts` fails on missing EN/FIL copy or orphan `guide.<area>.sN/tN` keys.
- Customers and store credit (ADR-0018): personal fields only on `customers` (audit rows name changed fields, never values); consent changes are rows in `customer_consent_events`; store credit is `customer_credit_entries` per (customer, legal entity), written with the sale or return in `record()`, posting to `CUSTOMER_STORE_CREDIT`. Store credit never becomes drawer cash: a return of a sale paid with credit gives that share back as credit to the payer (`creditShare`, trigger 0107); an exchange of a sale paid with credit or charged to a room is refused.
- Counter controls (ADR-0017): a price override is a `price_overrides` row approved by a second person's credentials (`AuthService.verifySecondPerson`) and consumed by `computeCart`; an exchange is `ReturnsService.record(..., {exchange})` + the new sale in one transaction (`exchangeCredit`).
- Integrations (ADR-0019): API keys are GET-only tenant sessions built in `AuthGuard` (scopes → permission codes; plan feature `api_access`); `key_hash` is never readable by the app. A new webhook topic goes in `WEBHOOK_TOPICS` (`@1pos/database`), `WEBHOOK_TOPIC_NAMES` (validation) and the admin copy; payloads carry ids only. Deliveries are written and settled only through the `webhook_*` definer functions (worker).
- Update `docs/STATUS.md` + `docs/BACKLOG.md` + `docs/LEFTOVER.md` at the end of each session.
